## 분석 기준

### 문제 인지

사전 지식 수준을 판정하고 리뷰 최상단에 표시:

| 등급 | 기준 | fetch |
|------|------|-------|
| ✅ 잘 앎 | 문제·풀이·제약 조건을 확실히 안다 | **금지** |
| ⚠️ 대략 앎 | 유형은 알지만 세부 불확실 | MCP puppeteer |
| ❌ 모름 | 문제를 모른다 (신뢰도 낮음 명시) | MCP puppeteer |

- ✅와 fetch는 상호 배타적.
- 사전 지식과 코드가 충돌하면 ⚠️로 하향 후 fetch.

**fetch 방법 (⚠️/❌만)**:
- BOJ: `mcp__{PUPPETEER}__puppeteer_navigate` → `https://www.acmicpc.net/problem/{번호}` (첫 navigate 시 `launchOptions: {"headless": false}`)
  추출: `mcp__{PUPPETEER}__puppeteer_evaluate` → `document.querySelector('#problem_description')?.innerText + '\n---\n' + document.querySelector('#problem_input')?.innerText + '\n---\n' + document.querySelector('#problem_output')?.innerText`
- 기타: 포스트의 문제 링크로 navigate 후 본문 추출.
- fetch 실패해도 ✅로 올리지 않는다.

### 구조

Phase 1이 처리하는 항목(frontmatter, 섹션, 코드 블록 태그, 수식, 복잡도 표기)은 건너뜀. 그 외 템플릿 위반만 지적.

### 아이디어

비어있으면 "아이디어 섹션 비어있음 — 건너뜀".

- **논리적 완결성**: "왜 이렇게 하면 되는지"가 있는가? 비약·오류는?
- **독자 이해도**: 설명만 읽고 구현할 수 있는가?
- **수식/오타**: 수식 일관성, 오타. (아이디어 소문자 vs 복잡도 $O(N)$ 불일치는 무시)
- **블로그 가치**: 독자에게 차별화된 가치가 있는가?
- **동일 문제 참조**: 다른 포스트를 참조하는 아이디어는 허용. 참조 대상이 충분히 설명하고 두 문제가 사실상 동일하면(예: 1158↔11866) 독립성 부족으로 지적하지 않는다.

### 코드

- **정확성**: 정상이면 "정확". 틀리면 상세히.
- **엣지 케이스**: 경계값을 구체적으로 명시하며 검증.
- **복잡도**: 시간/공간, 제약 대비 충분/부족.
- **개선점**: 적극 제안. "없음"은 구체적 근거 필수. 코드 예시 포함.
- **코드 스타일**: 관례 파일과 대조.

다국어: 로직 동일 → 하나만 상세 + 차이점. 로직 상이 → 각각 상세.

지적하지 않는 PS 관용 패턴:
- C++ `sizeof(arr)`, `find() != -1`, scanf/printf·cin/cout 혼용
- 학술적 C++ 스타일 제안 (`std::transform + toupper` 등)
- Java trailing newline (sb 내부 `\n` + println)
- 출력 끝 trailing newline (ans 끝에 `\n` 포함인데 `cout << ans << '\n'` 등)
- 인라인 수식 뒤 공백 (`$2$ 이 된다` 스타일은 의도된 관례)
- Java에서 문자열 출력 시 `BufferedWriter` 사용 (`StringBuilder` + `System.out`과 동등)
- Java/C++ 동일 문제 풀이의 출력 형식 차이 (소수 자릿수, setprecision 등) — 통과 코드면 의도적 상태, 지적 금지

### 리뷰 섹션

"없음."은 의도된 것. 내용 있으면 이상 여부만 확인.

### 태그 추천

각 포스트의 핵심 알고리즘/기법/자료구조를 분석해 적절한 태그를 추천한다. 부착 자체는 하지 않음 — *추천만*.

1. **어휘 파일 읽기 (필수)**: `/Users/mwzz6/Desktop/GITHUB/FickleBoBo.github.io/tools/tags.md`. 132 vocab entries (15 카테고리)의 closed vocabulary. 이 외 어휘는 사용 금지.
2. **부착 기준 — Future-you 검색 가치 테스트**: "이 태그로 검색한 미래의 사용자가 이 글을 *유용한 결과*로 받아들일 것이다" 일 때만 추천.
   - 글의 핵심 학습 포인트인 알고리즘/기법/자료구조 → 추천
   - `attach_policy: strict` 태그(stack/queue/deque/hash set·map/tree set·map/sorting)는 *문제 해결의 핵심일 때만* — 단순 보조/라이브러리 사용은 노이즈이므로 추천 X
   - 알고리즘 없이 언어 사용법 수준의 trivial 글 → `[warm up]` 단독 추천
   - 의심되면 추천 (recall > precision, strict 정책 제외)
3. **Specific 태그만 추천**: auto-companion으로 부모 ancestry가 자동 expand되므로 leaf/specific 태그만 적음. 예) `dijkstra` 추천 시 `shortest path`, `graph`는 적지 않음.
4. **multi-tag 적극**: 한 글에 여러 카테고리/기법이 모두 검색 가치 있으면 모두 추천 (예: `knapsack` + `greedy`).
5. **`technique` 카테고리 직접 추천 금지**: catch-all이라 너무 broad. 자식 태그(sliding window, two pointers 등)만 추천.
6. 사용자 PS 실력 범위는 **Platinum ~ Diamond V/IV**. 범위 밖 advanced 태그(link cut tree, splay tree, treap 등)는 추천하지 않음.

## Phase 3. Opus 등급 판정

모든 Agent 완료 후, 각 Agent의 요약표를 하나로 합친다 (1부터 연번).

아래 기준으로 **직접** 일괄 등급을 부여한다.

### 절대 금지 행동 (HARD STOP)

다음을 하면 즉시 멈추고 다시 시작:

1. **Spot check**: 일부 파일만 직접 read하고 나머지는 agent 출력으로 등급 부여 — 사용자 명시 허락 없이 절대 금지
2. **Agent 출력 그대로 받기**: Sonnet "지적 없음" → 그대로 A 부여 금지
3. **기억으로 태그/등급 답하기**: solved.ac 분류를 "기억"으로 답하는 것 금지. 실제 확인 필수
4. **시리즈 일괄 등급**: "동일 패턴이라 같은 등급"으로 묶어서 처리 금지
5. **분포 인위 조정**: "A가 너무 많아 보이니 몇 개 B로" — 분포 균형을 위해 등급 변경 금지
6. **사용자 영합 등급**: 사용자가 수정했다고 자동 A로 올리기 금지. 수정 내용이 실제로 지적사항을 해소했는지 확인 필수

### 등급 부여 전 강제 4단계 (각 파일마다)

A/B/C 어느 등급이든 부여하기 전에 다음 4단계를 *모두* 거쳐야 한다. 한 단계라도 빠지면 그 파일의 등급은 보류 ("검토 중") 처리.

#### (a) 파일 직접 read
- Read tool로 파일 전체를 읽었는가?
- agent 출력은 보조 자료. 원본은 내가 직접 본다.
- 36개면 36개 모두 read. 100개면 100개 모두 read.

#### (b) 코드 mental trace
- 자료구조 종류를 *한 줄씩* 확인했는가? (예: `set<string>`은 std::set / tree-based, `unordered_set`은 hash-based — 혼동 금지)
- 루프 경계, 종료 조건, 누적 변수 타입을 명시 확인했는가?
- 엣지 케이스 (N=1, 빈 입력, 최댓값) 처리를 확인했는가?

#### (c) 아이디어 비판적 평가
- 아이디어가 코드의 *핵심 통찰*을 설명하는가?
- 비-trivial 알고리즘인데 한 줄짜리 아이디어면 → 보강 필요 (B 후보)
- "트리비얼이라 짧은 아이디어 적절"은 *실제로 트리비얼할 때만* — 자동 적용 금지
- 핵심 단계가 "~~를 찾으면 된다" "~~ 처리하면 된다"로 추상화되어 있으면 → 그 단계가 진짜 핵심인지 확인. 핵심이면 vague는 B 사유.

#### (d) 태그 직접 대조
- tags.md의 attach_when 정의를 *읽고* 부착 기준 충족 확인
- solved.ac 분류를 *직접 확인* (puppeteer 등으로). "기억"으로 답하기 금지
- strict 정책 태그(stack/queue/deque/hash set·map/tree set·map/sorting): 풀이의 *핵심* 자료구조/기법인가? 단순 보조면 부착 X
- 코드의 자료구조와 태그가 일치하는가?
  - **C++ `set<T>` = std::set = tree set (hash set 아님)**
  - **C++ `unordered_set<T>` = hash set**
  - **C++ `map<K,V>` = tree map / `unordered_map<K,V>` = hash map**
  - Java `TreeSet/TreeMap` = tree, `HashSet/HashMap` = hash

### 등급 결정 시점 self-check

A/B/C를 적기 직전, 매번 자문:

> "내가 이 결론에 어떤 증거로 도달했지? (a)~(d) 4단계 다 했나? 안 했으면 다시."

기본값은 "**A 자격 증명 필요**"지 "**A unless caught**"가 아니다. 증거 없이 A 부여 금지.

### 등급 정의

| 등급 | 기준 |
|------|------|
| **S** | 완벽. 뛰어난 설명과 코드. trivial 문제는 S 거의 없음 |
| **A** | 깔끔. 정확한 코드, 적절한 설명, 진짜 흠 없음 |
| **B** | 무난. *진짜* 개선점 있음 (vague한 핵심 단계, 코드 품질 이슈, 핵심 누락) |
| **C** | 수정 필요. AC 코드라면 거의 없으나 idea/설명에 명백한 오류면 가능 |

### 판정 규칙

- 코드 버그 (오답, 오버플로우, 타입 불일치) → **C**
- 핵심 공식/근거 누락으로 포스트만으로 이해 불가 → **B 이하**
- "2중 반복문 활용" 수준의 형식적 아이디어 → **B**
- 사소한 지적 (출력 방식, 변수명) → **A** 유지
- 지적 없고 설명 뛰어남 → **S**

### 검증 방향: 포스팅 가치 ○ / 통과 코드 엣지 X

**평가할 것** (포스팅 가치 측면):
- 아이디어 퀄리티: 왜 이 접근이 작동하는지 설명되는가?
- 코드 가독성/스타일/idiom
- educational value: 독자가 배울 점이 있는가?
- 자료구조/기법 선택의 명확성

**평가하지 말 것** (통과 코드 보호):
- BOJ 명시 제약 내 이론적 엣지 케이스 ("만약 N이 더 크면" 등)
- 가상의 worst-case TLE/MLE
- 사용자가 리뷰 섹션에서 명시적으로 짚은 트레이드오프

다만 *코드의 자료구조 선택이 잘못 표현된 태그*는 "통과 코드"와 무관 — 즉시 정정.

### 함정 패턴 (능동 검증)

- Java `Arrays.sort(int[])` + N≥10⁵ → anti-quicksort TLE
- 곱셈/누적합 자료형 오버플로우 (BOJ 명시 제약 위반 시만)
- 출력 정밀도 (실수 문제)
- 재귀 깊이, 메모리

### 일관성

- 같은 유형의 지적 → 같은 등급.
- Agent 분석이 과도/부정확하면 무시하고 독립 판단.
- 지적사항 "—"은 지적 없음.

### 재리뷰 일관성

같은 대화 내에서 이전에 리뷰한 포스트를 다시 리뷰할 때:

- **파일 미변경 → 이전 등급 유지.** 같은 내용을 다르게 판단하지 않는다.
- 등급을 변경하려면 구체적 근거 필수: (1) 파일이 수정되어 특정 지적이 해소됨, (2) 사용자 피드백으로 관례가 변경됨 (예: "BufferedWriter 허용").
- 근거 없이 "다시 보니 괜찮다"는 등급 변경 사유가 아니다.

### 태그 일관성 보정 (Opus 능동 harmonize)

추천 태그는 Sonnet Agent가 생성한 것을 기본으로 가져오되, Opus는 **batch 전체를 보고 일관성 보정**을 수행한다. 청크별 독립 컨텍스트로 인해 같은 시리즈/같은 패턴이 청크 경계로 갈리면 다른 태그를 받을 수 있는 한계 보완.

**보정 절차**:

1. **시리즈/패턴 식별**: 문제 번호 인접·제목 패턴(예: "별 찍기 -", "카드", "큐", "스택", "덱") 기반으로 같은 시리즈 그룹화
2. **그룹 내 태그 통일**: 같은 시리즈는 같은 태그 부여를 원칙으로 함. Sonnet Agent들이 다르게 추천했으면 다음 우선순위로 결정:
   - (a) 사용자 PS 태그 통념(solved.ac/codeforces 표준) 우선
   - (b) `tools/tags.md`의 attach_when 정의에 더 부합하는 쪽
   - (c) 사용자 명확성: warm up vs implementation은 trivial 패턴/언어 사용법이면 warm up, 비-trivial 로직이면 implementation
3. **명백히 부적절한 추천 보정**: 시리즈 무관하게 단일 글의 태그가 attach_when에 안 맞으면 보정
4. **모호한 경우 사용자에게 결정 위임**: 보정 후에도 판단 어려우면 요약표 아래 "결정 필요" 섹션에 명시

**미래 개선 (corpus 누적 시)**:
- 현재는 모든 글이 `[Unlinked]` 상태라 batch 내 harmonize만 가능
- 태그 부착된 글이 쌓이면 Opus가 기존 태그된 글의 패턴을 reference로 활용하여 더 정확한 일관성 확보 가능 (별도 리팩토링 시점에 도입)

**보정 한계 명시**:
- Opus harmonize는 시리즈/패턴 기반 휴리스틱 → 100% 보장 아님
- 사용자 검토 단계는 여전히 필요
- 보정한 항목은 요약표에 *별도 표시*하여 사용자가 검수 가능하도록 함
